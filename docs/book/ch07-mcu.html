Chapter 7

Microcontrollers: Arduino, ESP32 & BLE

A microcontroller is a whole computer on one chip, and its peripherals are hardware you control by writing numbers to memory addresses. This chapter goes underneath digitalWrite(): registers, interrupts, timers and watchdogs on the ATmega328P; then the ESP32 with FreeRTOS, sleep modes and its pin quirks; then Bluetooth Low Energy from the radio up to GATT. It ends with a BLE-controlled RC car that stops when the link drops.

What a microcontroller is

Your laptop's CPU is surrounded by separate chips: RAM sticks, an SSD, a chipset, a network card. A microcontroller (MCU) puts a modest CPU, its memories and a collection of special-purpose hardware blocks (peripherals) on a single piece of silicon, together with the clock generation and power management that keep them running. It costs from a few cents to a few dollars, starts in milliseconds and can run for years on a battery. The trade-off is scale: the ATmega328P in an Arduino Uno has 32 KB of flash and 2 KB of RAM, and runs at 16 MHz. Even the comparatively huge ESP32 has around 520 KB of on-chip SRAM.

The main parts, which you'll find on every MCU datasheet's block diagram:

  • CPU core. AVR (8-bit) on the ATmega328P; Xtensa LX6 (32-bit, dual core) on the original ESP32; LX7 on the ESP32-S3; RISC-V on the ESP32-C3/C6; ARM Cortex-M on STM32 and nRF52.
  • Flash. Non-volatile program memory. On the AVR it's on chip; on the ESP32 it's a separate SPI flash chip inside the module, executed through a cache.
  • SRAM. Variables, the stack and the heap. Lost at power-off.
  • Peripherals. GPIO ports, timers, UARTs, SPI and I²C controllers, ADCs, PWM generators, DMA, and on the ESP32 the radios. Each is a little state machine that runs in parallel with the CPU.
  • Buses. The internal wiring that connects them. The CPU, DMA and memories sit on a fast bus; slower peripherals hang off a bridge to a slower one (ARM calls these AHB and APB, and Espressif uses the same terms). The bus clock is why ESP32 peripherals talk about the "80 MHz APB clock".
  • Clock tree. A crystal or internal RC oscillator, often multiplied up by a PLL (phase-locked loop) and divided down for each domain. Every timer, baud rate and PWM frequency is ultimately a fraction of one of these clocks.
  • Interrupt controller, reset and power management (brown-out detector, watchdog, sleep modes), and debug (JTAG/SWD, or the AVR's debugWIRE).
👩‍💻 Developer's analogy: an MCU is a single-process OS with memory-mapped devices

There's no kernel between you and the hardware. Your firmware is the only process, it owns every address, and devices are memory-mapped: a peripheral's control registers appear at fixed addresses, just as /dev/mem exposes them on Linux. Interrupts are your signal handlers, timers are your setInterval, DMA is sendfile(), and the watchdog is a systemd watchdog that hard-reboots the machine if you stop petting it. The analogy breaks in one important place: nothing protects you from yourself. A stray pointer can corrupt the stack, rewrite a peripheral's configuration, or (on chips with writable flash) erase your program. Many MCUs do have an MPU (memory protection unit), but it's opt-in.

Your ESP32 firmware sets a PWM frequency of 20 kHz and an I²C clock of 400 kHz. Where do both of those frequencies ultimately come from?
  1. Each peripheral contains its own independent crystal
  2. A shared clock source (crystal or RC oscillator), multiplied by a PLL and divided down by each peripheral's prescalers
  3. The CPU toggles the pins in software at those rates
  4. The USB connection provides a timing reference
The ESP32's 40 MHz crystal feeds a PLL; the CPU runs at up to 240 MHz and most peripherals at the 80 MHz APB clock (some can select other sources). Each peripheral divides its source down. That's why some frequencies are achievable exactly and others only approximately, as with the UART baud rates in Chapter 6.

Memory-mapped registers: the real API

Every peripheral is controlled through registers: small words of memory, at fixed addresses, wired directly to the hardware. Writing a bit doesn't store a value somewhere for later; it closes a switch in the silicon. On the ATmega328P each 8-pin port has three registers:

RegisterAddress (data space)Meaning of bit \(n\)
DDRB0x24Data direction: 1 = pin \(n\) is an output, 0 = input
PORTB0x25For an output: the level to drive. For an input: 1 enables the internal pull-up
PINB0x23Read the actual pin level. Writing a 1 toggles the corresponding PORTB bit

Arduino pin 13, the one with the on-board LED, is PB5: bit 5 of port B. So "turn the LED on" is: set bit 5 of DDRB (make it an output), then set bit 5 of PORTB (drive it high). In C you manipulate individual bits with masks and the bitwise operators you already know:

DDRB  |=  (1 << DDB5);       // set bit 5: PB5 is an output
PORTB |=  (1 << PORTB5);     // set bit 5: drive high, LED on
PORTB &= ~(1 << PORTB5);     // clear bit 5: drive low, LED off
PORTB ^=  (1 << PORTB5);     // flip bit 5 (read-modify-write)
PINB   =  (1 << PINB5);      // hardware toggle: one write, no read needed
bool pressed = !(PIND & (1 << PIND2));   // read pin 2 (active low with pull-up)

Each of those set/clear lines compiles to a single 2-cycle SBI or CBI instruction: 125 ns at 16 MHz. By comparison, Arduino's digitalWrite(13, HIGH) takes a few microseconds, because it looks up the pin number in tables (pin → port, pin → bit mask, pin → timer), turns off any PWM on that pin, and disables interrupts briefly around the write. It's about 30–50 times slower, which almost never matters and occasionally matters a lot (bit-banging a protocol, toggling a pin in a fast ISR).

👩‍💻 Read-modify-write is a race condition

PORTB |= mask is three steps: read PORTB, OR, write it back. If an interrupt fires between the read and the write and changes another bit of PORTB, your write-back silently undoes the ISR's change: a classic lost update. The AVR dodges this for single bits because the compiler emits atomic SBI/CBI instructions for constant masks, but not for multi-bit or variable masks. The ESP32 avoids it by design with paired write-1-to-set and write-1-to-clear registers (GPIO_OUT_W1TS_REG, GPIO_OUT_W1TC_REG): writing a 1 to bit \(n\) sets (or clears) only pin \(n\), and zeros mean "leave alone". No read, no race. It's the hardware equivalent of an atomic fetch_or.

Datasheets also show how each pin can be taken over by a peripheral: the "alternate functions". PB3 is also MOSI and the output of Timer2's compare unit A (OC2A); PD0 and PD1 are the UART's RX and TX. Enabling a peripheral overrides the PORT/DDR settings for its pins. On the AVR, these assignments are fixed. On the ESP32 they're mostly flexible, as we'll see.

The Arduino layer vs bare metal

The Arduino framework is a hardware abstraction layer plus a build system. pinMode, digitalWrite, analogRead, Serial, Wire and SPI wrap the registers in a portable API, millis() is driven by a Timer0 overflow interrupt, and setup()/loop() are called from a hidden main(). Arduino-ESP32 wraps ESP-IDF in the same way, which is why you can mix the two. It's an excellent starting point and a perfectly respectable production choice for small projects. Know what it costs:

  • Hidden resources. Timer0 is taken (by millis()), tone() uses Timer2, and the Servo library takes Timer1, which disables analogWrite() on pins 9 and 10. If two libraries fight over a timer, the symptoms look random.
  • Hidden time. Serial.print blocks when its 64-byte buffer is full; delay() burns the CPU; analogRead() takes about 110 µs on an Uno.
  • Hidden interrupts. Timer0's overflow ISR runs every 1.024 ms and adds jitter to anything time-critical.

Going bare-metal doesn't mean abandoning Arduino. It means knowing which register a function touches, so you can drop down a level for the one hot path that needs it.

Interrupts

Your loop() can check a button a million times a second and still miss a 2 µs encoder pulse that happens while it's busy printing. Interrupts invert the control flow: the hardware notices the event, finishes the current instruction, saves a little state, and jumps to a function you registered, the interrupt service routine (ISR). When the ISR returns, the interrupted code resumes as if nothing happened. Sources include pin changes, timer matches, a byte arriving on a UART, an ADC conversion finishing, or a DMA transfer completing.

The sequence, in more detail, is:

  1. The peripheral sets an interrupt flag bit in one of its registers. This happens even if interrupts are disabled; the flag simply stays set (it's "pending").
  2. If that interrupt is enabled (its enable bit and the global interrupt enable are both set), the CPU finishes its current instruction and saves the program counter.
  3. It looks up the ISR's address in the vector table and jumps there. The compiler-generated prologue pushes any registers the ISR uses.
  4. The ISR runs. On most peripherals, entering the ISR (or reading a data register) clears the flag; on some, your code must clear it explicitly. Forget, and the ISR re-triggers forever.
  5. The epilogue restores registers and a return-from-interrupt instruction resumes the main code.

The time from event to the first line of your ISR is the interrupt latency: a handful of cycles in hardware plus the prologue, so roughly 1–2 µs on a 16 MHz AVR, and on the order of a couple of microseconds through ESP-IDF's interrupt dispatcher on an ESP32. Latency grows whenever interrupts are disabled (inside another ISR on the AVR, or in a critical section) because the new interrupt has to wait.

// Arduino (AVR): count button presses on pin 2 (INT0)
volatile uint16_t presses = 0;          // shared with the ISR: must be volatile

void onPress() {                        // runs in interrupt context
    presses++;                          // keep it short!
}

void setup() {
    pinMode(2, INPUT_PULLUP);
    attachInterrupt(digitalPinToInterrupt(2), onPress, FALLING);
    Serial.begin(115200);
}

void loop() {
    noInterrupts();                     // a 16-bit read takes two instructions on an 8-bit CPU:
    uint16_t n = presses;               // without this, the ISR could change it halfway
    interrupts();
    Serial.println(n);
    delay(200);
}

Why volatile, and why it isn't enough

The optimiser assumes that a variable only changes when the code it can see changes it. In while (!flag) {} it sees nothing inside the loop that writes flag, so it may load flag once into a register and spin forever. Declaring it volatile forces a real memory read every time. Any variable written in an ISR and read elsewhere (or vice versa) must be volatile. So must pointers to hardware registers, which is how the AVR headers define PORTB.

But volatile does not make access atomic. On an 8-bit AVR, reading a 16- or 32-bit variable takes several instructions, and an interrupt can land between them and leave you with a torn value: half old bytes and half new. The fix is a short critical section (noInterrupts()/interrupts(), or ATOMIC_BLOCK(ATOMIC_RESTORESTATE) from <util/atomic.h>) around the copy. On the 32-bit ESP32 aligned 32-bit reads are atomic, but read-modify-write sequences such as count++ are not, and with two cores you need real synchronisation: portENTER_CRITICAL with a spinlock, FreeRTOS primitives, or C11 atomics.

⚠️ Misconception: "volatile makes it thread-safe"

volatile only means "don't cache this in a register, and don't remove or reorder accesses to it relative to other volatile accesses". It says nothing about atomicity, and nothing about ordering relative to non-volatile memory. It is the right tool for hardware registers and ISR flags on a single core. For anything more, use a critical section, an atomic type or an RTOS primitive. This is the same lesson as Java's or C#'s volatile, with sharper edges.

Keep ISRs short

While an ISR runs, the main code is frozen, and (on the AVR, and at the same or lower priority elsewhere) other interrupts wait. Long ISRs cause three kinds of trouble: they add latency to every other interrupt, they starve the main loop, and if the same event recurs before the ISR finishes, the hardware can only remember one pending occurrence. The rest are silently lost.

The standard pattern is do the minimum, defer the rest: in the ISR, capture the timestamp or the data byte, set a flag or push to a queue, and return. Do the processing in the main loop or, with an RTOS, in a task that the ISR wakes. Things that don't belong in an ISR: Serial.print, delay(), floating-point maths on chips without an FPU, heap allocation, I²C transactions, and anything that waits for another interrupt (which can never arrive while you're blocking it).

Which of these are reasonable things to do inside an ISR? (Select all that apply.)
  1. Increment a volatile counter
  2. Print a debug message with Serial.println()
  3. Read a byte from the UART data register into a ring buffer
  4. Wait in a loop for an I²C transaction to complete
  5. Record the current timer value as a timestamp and set a flag
  6. Send an item to a FreeRTOS queue with xQueueSendFromISR()
Capture, timestamp, flag, enqueue: all fast and non-blocking. Printing can block when the buffer is full and itself relies on interrupts; waiting on I²C may wait for an interrupt that can't run. In FreeRTOS, only API functions ending in FromISR may be called from an ISR.

Debouncing

Mechanical contacts don't close cleanly. The metal bounces, making and breaking contact several times over a few hundred microseconds to a few milliseconds. To an interrupt on a falling edge, one press looks like five. There are two cures, and robust designs often use both:

  • Hardware: an RC low-pass filter (for example 10 kΩ and 100 nF, \(\tau = 1\) ms) smooths the bounces into a single slow edge, and a Schmitt-trigger input (most MCU pins have some hysteresis; a 74HC14 has a lot) turns that slow edge back into one clean transition. Chapter 3 has the RC maths; Chapter 6 explained why slow edges need hysteresis.
  • Software: after the first edge, ignore further edges for a lockout time (10–50 ms), or sample the pin periodically from a timer and only accept a new state after it has been stable for several samples.
// Software debounce: accept a press only if 30 ms have passed since the last one
volatile uint32_t lastEdgeMs = 0;
volatile bool pressEvent = false;

void IRAM_ATTR onButton() {             // IRAM_ATTR: ESP32 ISRs must live in RAM
    uint32_t now = millis();
    if (now - lastEdgeMs > 30) {        // unsigned subtraction handles millis() wrap-around
        pressEvent = true;
    }
    lastEdgeMs = now;
}

Timers, PWM and the watchdog

A hardware timer is a counter register that increments on every tick of a clock. That clock is the system clock divided by a prescaler (1, 8, 64, 256 or 1024 on the AVR). Comparators watch the counter: when it equals a compare register (OCR), the timer can raise an interrupt, toggle or set a pin, or reset the counter to zero. That last option is CTC mode ("clear timer on compare"), and it turns the timer into a precise periodic event generator:

$$f_{\text{interrupt}} = \frac{f_{clk}}{N\,(1 + \text{OCR})} \qquad f_{\text{toggle pin}} = \frac{f_{clk}}{2N\,(1 + \text{OCR})}$$

CTC mode. \(N\) is the prescaler; the counter runs 0, 1, …, OCR, so one period is OCR + 1 ticks. A pin that toggles on each match completes one cycle every two matches.

Worked example. You want a 1 kHz control-loop interrupt on a 16 MHz Uno. With \(N = 64\), one tick is 4 µs, and 1 ms is 250 ticks, so OCR = 249. With \(N = 8\) you'd need OCR = 1999, which doesn't fit an 8-bit timer (max 255) but fits the 16-bit Timer1. Always pick the smallest prescaler whose OCR still fits the timer's width: it gives the finest resolution.

In Figure 7.6, using the 8-bit timer at 16 MHz, produce an interrupt rate of exactly 1000 Hz.
Prescaler 64 and OCR = 249: \(16\,000\,000 / (64 \times 250) = 1000\) Hz exactly. With prescaler 256 you'd need OCR = 61.5, impossible; the nearest values give 1008 Hz or 992 Hz, an error of 0.8%.
A 16 MHz AVR timer in CTC mode, prescaler 8, toggles a pin on each compare match. What OCR value makes the pin output an 8 kHz square wave?
Use \(f_{toggle} = f_{clk}/(2N(1+\text{OCR}))\) and solve for OCR.
\(1 + \text{OCR} = 16\,000\,000/(2 \times 8 \times 8000) = 125\), so OCR = 124. The compare interrupt itself runs at 16 kHz; the pin needs two toggles per cycle.
// AVR Timer2: 1 kHz interrupt in CTC mode
volatile uint32_t ticks = 0;
void setup() {
    cli();
    TCCR2A = (1 << WGM21);       // CTC: clear on compare match A
    TCCR2B = (1 << CS22);        // Timer2 prescaler 64
    OCR2A  = 249;                // 16 MHz / 64 / 250 = 1000 Hz
    TIMSK2 = (1 << OCIE2A);      // enable the compare-match-A interrupt
    sei();
}
ISR(TIMER2_COMPA_vect) { ticks++; }

// ESP-IDF: the high-resolution esp_timer does the same job without touching hardware timers
static void control_cb(void *arg) { /* runs every 1 ms in the esp_timer task */ }
const esp_timer_create_args_t args = { .callback = control_cb, .name = "ctl" };
esp_timer_handle_t t;
esp_timer_create(&args, &t);
esp_timer_start_periodic(t, 1000);   // period in microseconds

PWM (Chapter 6) is the same machinery with the counter running freely from 0 to TOP and a pin that is set at 0 and cleared when the counter passes the compare value. Timers also capture: on an input edge they copy the counter into a register, timestamping the edge with clock-cycle precision and no software latency. That's how you measure RC receiver pulse widths or an ultrasonic sensor's echo properly.

The watchdog

Firmware hangs. An I²C bus locks up (Chapter 6), a loop waits for a flag that never comes, a stack overflow corrupts a return address. A watchdog timer (WDT) is an independent countdown, clocked from its own oscillator, that resets the chip if the firmware doesn't "kick" (reset) it in time. You kick it from one place in your main loop that's only reached when everything is healthy, never from a timer ISR (which would keep running while the main loop is stuck).

#include 
void setup() { wdt_enable(WDTO_250MS); }   // reset if not kicked within ~250 ms
void loop()  { readSensors(); updateMotors(); wdt_reset(); }

// ESP-IDF task watchdog: each subscribed task must check in
esp_task_wdt_add(NULL);                     // subscribe the current task
while (true) { do_work(); esp_task_wdt_reset(); vTaskDelay(pdMS_TO_TICKS(10)); }

For a robot, a watchdog reset is also a safety event: when the chip resets, its pins revert to inputs. Make sure that "all MCU pins floating" means "motors off" in hardware, with pull-downs on motor-driver enable and PWM inputs. That costs two resistors and is the cheapest failsafe you'll ever add.

A timer ISR sets bool dataReady = true; and loop() waits with while (!dataReady) {}. It works with optimisation off and hangs forever with -O2. What's the fix?
  1. Add delay(1) inside the while loop
  2. Declare the flag volatile bool dataReady;
  3. Make the ISR longer so the flag is set for more time
  4. Use an int instead of a bool
Without volatile, the compiler hoists the load out of the loop because nothing in the loop writes the flag. delay(1) might hide the bug by forcing a reload after a function call, which is exactly why this bug comes and goes.

The ESP32

Espressif's ESP32 family is the default brain for hobby robots that need a radio. The original ESP32 has two 32-bit Xtensa LX6 cores at up to 240 MHz, about 520 KB of SRAM, Wi-Fi (802.11 b/g/n) and Bluetooth (Classic and BLE 4.2), and a long list of peripherals: three UARTs, two I²C, several SPI controllers, 16 PWM channels (LEDC) plus a motor-control PWM unit (MCPWM), a pulse counter for encoders, the RMT peripheral (originally for infrared remotes, now used for WS2812 LEDs and DShot), a CAN controller (TWAI), two ADCs and two DACs, capacitive touch and a low-power coprocessor. Newer members trade features: the ESP32-S3 (dual LX7, BLE 5, native USB, vector instructions), the ESP32-C3 (single RISC-V core, BLE 5, cheap) and the ESP32-C6 (adds Wi-Fi 6 and 802.15.4 for Thread/Zigbee). Most of what follows applies to all of them, but pin numbers and quirks differ. Always check the datasheet for the exact chip.

You rarely use the bare chip. A module (ESP32-WROOM-32E, ESP32-S3-WROOM-1, ...) adds the flash chip, the 40 MHz crystal, the RF matching network and the antenna under a metal shield, already certified for radio emissions. A dev board adds a USB-serial converter, a 3.3 V regulator, and BOOT and EN buttons. That extra hardware matters later when we talk about battery life.

Two cores

On the dual-core parts, ESP-IDF runs a symmetric-multiprocessing build of FreeRTOS. By convention the Wi-Fi and Bluetooth stacks run on core 0 ("PRO_CPU") and Arduino's loop() runs on core 1 ("APP_CPU"). You can pin your own tasks to either. Putting time-critical motor control on core 1 keeps it away from radio activity, but remember the earlier warning: anything shared between cores needs real synchronisation, not just volatile.

Strapping pins and pins to avoid

At reset, before any of your code runs, the ESP32 samples a few strapping pins to decide how to boot. Hardware attached to those pins can therefore stop the board from booting at all, and it's the most common "it worked on the breadboard, not on my PCB" bug:

The ESP32's ADC: usable, with care

The original ESP32's ADCs are its weakest peripheral, and you should know their quirks before you design a battery monitor around one:

  • ADC2 is shared with the Wi-Fi driver. While Wi-Fi is running, ADC2 reads fail (ESP-IDF returns a timeout error). Put analog inputs on ADC1 channels: GPIO32–39.
  • Attenuation sets the range. The ADC itself measures about 0–1 V. An input attenuator extends that: Espressif's documentation gives recommended ranges of roughly 100–950 mV at 0 dB, up to roughly 150–2450 mV at the highest setting (called 11 dB in older code, 12 dB in IDF 5). Outside those windows the response is nonlinear.
  • It's nonlinear and the reference varies from chip to chip. Near 0 V the reading sticks at zero; near the top it saturates early and curves. The internal reference is around 1.1 V but varies by roughly ±10% between chips, so Espressif burns a per-chip calibration value into eFuse. Use the calibration API (adc_cali_* in IDF 5, or analogReadMilliVolts() in Arduino-ESP32), which applies it.
  • It's noisy. Average several samples, add 100 nF at the pin (Chapter 6 explained why), and keep the signal in the linear window with a divider.
Your ESP32 robot reads its battery voltage on GPIO25. It works in a test sketch, but as soon as you enable Wi-Fi, the readings fail. Why?
  1. Wi-Fi transmissions add too much noise to the battery line
  2. GPIO25 is on ADC2, which the Wi-Fi driver uses; move the divider to an ADC1 pin (GPIO32–39)
  3. GPIO25 is a strapping pin
  4. Wi-Fi changes the ADC attenuation
ADC2 channels (GPIO0, 2, 4, 12–15, 25–27) are unusable while Wi-Fi is active. GPIO34–39 are ideal for analog inputs: input-only pins on ADC1.

The GPIO matrix

On the AVR, the UART's TX is PD1, full stop. On the ESP32 most peripheral signals pass through a GPIO matrix, a big crossbar that can route almost any peripheral input or output to almost any GPIO. That's why Wire.begin(sda, scl) and uart_set_pin() take pin numbers. The routing adds a few nanoseconds of delay, so the fastest signals (the flash's SPI bus, high-speed SPI at 80 MHz) use dedicated IO_MUX pins instead. For a robot it means a lot of freedom in PCB layout: route the board for clean wiring, then tell the firmware where everything ended up.

ESP-IDF vs Arduino-ESP32

ESP-IDF is Espressif's official framework: CMake builds, menuconfig for configuration, FreeRTOS, and C APIs for every peripheral and protocol (Wi-Fi, BLE through NimBLE or Bluedroid, HTTP, MQTT, OTA, flash encryption, secure boot). Arduino-ESP32 is a layer on top of it. You get the Arduino API and libraries, and you can still call IDF functions directly. A good path: start in Arduino (fast results, huge library ecosystem), use IDF APIs where Arduino hides something you need (RMT, MCPWM, sleep, power management), and move to pure IDF (or PlatformIO with the IDF framework) when the project needs reproducible builds, fine-grained configuration or production features like secure boot.

FreeRTOS: tasks, queues and priorities

A super-loop (loop() calling everything in turn) works until one part needs to wait. The BLE stack waits for packets, the IMU driver waits for I²C, the logger waits for the SD card, and the motor controller must run every 10 ms regardless. A real-time operating system lets you write each of those as an independent task with its own stack, as if it had the CPU to itself, and a scheduler switches between them.

FreeRTOS's scheduler is simple and predictable, which is what "real-time" really means:

  • Every task has a priority. The scheduler always runs the highest-priority task that is ready. Equal priorities share time slices of one tick (1 ms by default on ESP-IDF).
  • A task that calls vTaskDelay(), waits on a queue, a semaphore or an event, is blocked and uses no CPU until the event happens or its timeout expires.
  • Scheduling is preemptive: when a higher-priority task becomes ready (because an ISR gave it a semaphore, say), it runs immediately, interrupting whatever lower-priority task was running.
  • When nothing is ready, the idle task runs (and can put the CPU into light sleep).

The consequence: a high-priority task that never blocks starves everything below it. In FreeRTOS, "busy-waiting" isn't just wasteful, it's a correctness bug.

// ESP-IDF: an ISR feeds a queue; a task does the work
static QueueHandle_t cmd_q;

typedef struct { int16_t throttle, steering; } cmd_t;

static void motor_task(void *arg) {
    cmd_t cmd = {0};
    TickType_t last = xTaskGetTickCount();
    for (;;) {
        cmd_t c;
        while (xQueueReceive(cmd_q, &c, 0) == pdTRUE) cmd = c;   // drain: keep the newest
        apply_motors(cmd.throttle, cmd.steering);
        vTaskDelayUntil(&last, pdMS_TO_TICKS(10));              // exact 100 Hz, no drift
    }
}

void app_main(void) {
    cmd_q = xQueueCreate(8, sizeof(cmd_t));
    // name, stack bytes, arg, priority, handle, core
    xTaskCreatePinnedToCore(motor_task, "motor", 4096, NULL, 10, NULL, 1);
}

// Elsewhere (a BLE callback, a UART task...):  xQueueSend(cmd_q, &c, 0);
👩‍💻 Developer's analogy: tasks are threads, queues are channels

A FreeRTOS task is a thread with a fixed-size stack you choose up front (too small and it overflows silently, unless you enable stack checking). A queue is a bounded, thread-safe channel that copies items by value, just like a Go channel or a BlockingQueue. Semaphores, mutexes (with priority inheritance) and event groups are what you'd expect. Two differences from desktop threads: priorities are strict (there's no fairness; a ready high-priority task always wins), and there's no virtual memory, so every stack is real RAM you pay for. uxTaskGetStackHighWaterMark() tells you how close each task came to overflowing.

Power modes, battery life and OTA

An ESP32 that's awake with Wi-Fi transmitting can draw 200–300 mA in bursts. One that's in deep sleep draws around 10 µA. That's a ratio of more than 10,000, and battery-powered design is the art of spending as much time as possible in the low state. The main modes, roughly:

ModeWhat runsTypical current (chip)Wake-up
Active, radio TXEverything~100–250 mA (bursts higher)—
Modem sleepCPU on, radio off between beacons~20–30 mA at 80 MHz, more at 240 MHz—
Light sleepCPU paused, RAM and state kept~0.8 mA~1 ms; resumes where it stopped
Deep sleepOnly the RTC domain (timer, RTC memory, ULP)~10 µAReboots into app_main(); only RTC memory survives
HibernationRTC timer only~5 µALike deep sleep, fewer sources

The average current decides battery life. If the device is active at \(I_a\) for \(t_a\) seconds every \(T\) seconds and sleeps at \(I_s\) the rest of the time:

$$\bar I = \frac{I_a t_a + I_s (T - t_a)}{T} \qquad \text{life} \approx \frac{\text{capacity}}{\bar I}$$

Duty-cycled average current. In practice derate the capacity by 20–30% for temperature, ageing and the cut-off voltage.

Worked example. A weather node wakes every 10 minutes, spends 2 s at 80 mA connecting to Wi-Fi and sending a reading, and sleeps at 10 µA. \(\bar I = (80 \times 2 + 0.01 \times 598)/600 = 0.277\) mA. A 1000 mAh cell lasts \(1000/0.277 \approx 3600\) hours, about five months. Note where the charge goes: the sleep current contributes 0.01 mA, the wake-ups 0.267 mA. Halving the time spent connected helps far more than a better sleep current. That's why low-power designs cache the Wi-Fi channel and use static IPs, or use ESP-NOW or BLE, which connect in milliseconds instead of seconds.

⚠️ The dev board, not the chip, sets your sleep current

Measure a typical ESP32 dev board in deep sleep and you'll see milliamps, not microamps: the USB-serial chip, the power LED, and a regulator like the AMS1117 (several mA of quiescent current) are all still powered. For battery work use a board designed for it, or your own PCB with a low-IQ LDO (Chapter 5) and the USB bridge powered only from USB. Also check every pull-up: a 10 kΩ pull-up on a line held low during sleep costs 330 µA, thirty times the chip's own sleep current.

In Figure 7.10, keeping a 1000 mAh battery and wake-ups of 80 mA for 2 s, find settings that reach one year (365 days) of battery life.
You need \(\bar I \le 1000\,\text{mAh}/8760\,\text{h} = 0.114\) mA. With a 10 µA sleep current, the wake-ups may use at most about 0.104 mA, so \(160\,\text{mA·s}/T \le 0.104\) mA, giving \(T \ge 1540\) s: one wake-up every 26 minutes or so. With a 5 mA dev-board sleep current it's impossible at any interval.
A sensor node draws 80 mA for 2 s every 600 s and 10 µA the rest of the time. Ignoring derating, how many hours does a 1000 mAh battery last?
Average current \(= (80 \times 2 + 0.010 \times 598)/600\) mA.
\(\bar I = (160 + 5.98)/600 = 0.2766\) mA, so life \(= 1000/0.2766 \approx 3614\) h ≈ 150 days. With a realistic 25% derating, plan on about 110 days.

Over-the-air updates

Once the robot is assembled, the USB port is buried. OTA (over-the-air) updates let the firmware download and install a new version of itself. The ESP32's partition table reserves two application slots, ota_0 and ota_1, plus a small otadata partition recording which one to boot. The running firmware writes the new image into the other slot, verifies it, flips otadata and reboots. With rollback enabled, the new image must call esp_ota_mark_app_valid_cancel_rollback() after it has proved itself (connected to Wi-Fi, passed a self-test); if it crashes before that, the bootloader reverts to the old slot. It's the same blue/green deployment pattern you'd use for a web service.

// ESP-IDF: download and install firmware over HTTPS
esp_http_client_config_t http = { .url = "https://example.com/rc-car.bin", .cert_pem = server_cert };
esp_https_ota_config_t ota = { .http_config = &http };
if (esp_https_ota(&ota) == ESP_OK) esp_restart();

// Arduino-ESP32: OTA from the Arduino IDE / PlatformIO over the local network
ArduinoOTA.setPassword("change-me");
ArduinoOTA.begin();          // in setup()
ArduinoOTA.handle();         // call regularly in loop()
⚠️ OTA on a robot

An update reboots the MCU, and during the download the CPU and radio are busy. Never allow an OTA while the motors are armed: require the vehicle to be disarmed and stationary, and stop the motors before the download starts. Protect the update channel too (a password at minimum; signed images with secure boot for anything serious), or anyone on the network can replace your firmware.

Bluetooth Low Energy from the radio up

Bluetooth Low Energy (BLE, marketed as Bluetooth Smart for a while) shares a name with "Classic" Bluetooth (headphones, serial-port profiles) but is a different protocol, designed from scratch for devices that send small amounts of data and sleep most of the time. It's what your phone uses to talk to fitness bands, and it's the easiest way to control a robot from a phone, because every phone has it and no pairing app is needed beyond a generic one. The standard reference for this section is Townsend, Cufí, Akiba and Davidson's Getting Started with Bluetooth Low Energy.

The radio: 40 channels at 2.4 GHz

BLE uses the 2.4 GHz ISM band (2400–2483.5 MHz), shared with Wi-Fi, microwave ovens and many RC links. It divides the band into 40 channels, 2 MHz apart. Three of them, channels 37, 38 and 39 (at 2402, 2426 and 2480 MHz), are advertising channels, deliberately placed in the gaps between the most common Wi-Fi channels 1, 6 and 11. The other 37 are data channels, used once two devices are connected, with frequency hopping: each connection event happens on a different channel, following a pattern both sides know, and channels that keep failing can be removed from the map ("adaptive frequency hopping"). The basic PHY sends 1 Mbit/s; Bluetooth 5 added a 2 Mbit/s PHY (faster, slightly shorter range) and a Coded PHY at 125 or 500 kbit/s that adds forward error correction for roughly four times the range. The ESP32-S3 and C3 support both; the original ESP32 only has the 1 Mbit/s PHY.

Advertising and scanning

Before any connection, a device makes itself known by advertising: every advertising interval (20 ms to 10.24 s) it wakes, transmits a short packet on channel 37, then 38, then 39, and goes back to sleep. A random delay of 0–10 ms is added to each interval so that two advertisers that happen to collide don't keep colliding forever. A legacy advertising packet carries up to 31 bytes of payload: flags, the device name, service UUIDs, manufacturer data, transmit power.

A scanner listens on one advertising channel for a scan window, every scan interval, cycling through the three channels. Discovery happens when an advertising packet lands inside a scan window on the channel being listened to. The scanner's duty cycle (window ÷ interval) and the advertiser's interval together set how quickly devices find each other, and both cost power: the advertiser per packet, the scanner for every millisecond its receiver is on.

GAP: who does what

The Generic Access Profile (GAP) defines roles and procedures. There are four roles:

  • Broadcaster: advertises, never connects (a beacon). Observer: only scans.
  • Peripheral: advertises and accepts a connection. Your robot, a sensor or a heart-rate band.
  • Central: scans and initiates connections. A phone, a laptop, or an ESP32 acting as the remote control.

A device can play several roles at once (an ESP32 can be a central to a sensor and a peripheral to a phone). Note that GAP roles say who connects, not who serves data. That's GATT's business, below.

Connections: interval, latency and supervision timeout

Once connected, the two devices meet at regular connection events. At each event the central transmits first, the peripheral answers, and they can exchange several packets back and forth before both go back to sleep until the next event. Three parameters, set by the central (the peripheral can request changes), control everything:

  • Connection interval: 7.5 ms to 4 s, in steps of 1.25 ms. Short intervals mean low latency and high throughput; long ones mean low power.
  • Peripheral latency (formerly "slave latency"): the number of consecutive events the peripheral may skip when it has nothing to send. It saves the peripheral's power without slowing the peripheral's own uplink, but data to the peripheral can now wait up to \((1 + \text{latency})\) intervals.
  • Supervision timeout: 100 ms to 32 s. If no valid packet is received for this long, the link is declared lost. The specification requires
$$t_{\text{supervision}} \gt 2\,(1 + \text{latency}) \times t_{\text{interval}}$$

The supervision timeout must exceed two "effective" intervals, so that a couple of missed events can't kill a healthy link.

For an RC vehicle the supervision timeout is a safety parameter: it is how long the robot keeps executing its last command after the phone walks out of range, unless you add an application-level failsafe (and you will, later in this chapter).

For example interval 15 ms, latency 0, timeout 100–250 ms. Peripheral latency must be 0 (or the interval tiny) because commands flow to the peripheral. A connection uses a 30 ms interval and a peripheral latency of 4. What's the smallest supervision timeout the rule allows? (The actual value must be strictly greater.)
\(2 \times (1 + \text{latency}) \times \text{interval}\).
\(2 \times 5 \times 30\) ms \(= 300\) ms, so the timeout must be above 300 ms (it's set in 10 ms units, so 310 ms is the smallest legal value). With that latency the peripheral may legitimately stay silent for 150 ms, so a failsafe on the car that triggers after 100 ms of silence would fire constantly.

GATT: services, characteristics and descriptors

Once connected, data is organised by the Generic Attribute Profile (GATT), which sits on top of the Attribute Protocol (ATT). The device holding the data is the GATT server (usually the peripheral; your robot); the one accessing it is the client (the phone). The server's data is a flat table of attributes, each with a 16-bit handle, a type (a UUID) and a value, organised into a hierarchy:

  • A profile is just a specification of which services a kind of device has (the Heart Rate Profile, for instance). It doesn't appear on the wire.
  • A service groups related data: Battery Service (UUID 0x180F), Device Information (0x180A), or your own "RC Control" service.
  • A characteristic is one value with properties that say what a client may do with it: read, write (acknowledged), write without response (unacknowledged, faster), notify (server pushes updates, unacknowledged) and indicate (server pushes updates, acknowledged).
  • A descriptor adds metadata to a characteristic. The important one is the Client Characteristic Configuration Descriptor (CCCD, UUID 0x2902): the client writes 0x0001 to it to enable notifications (0x0002 for indications). Until a client does that, the server isn't allowed to notify.

UUIDs come in two sizes. The Bluetooth SIG assigns 16-bit UUIDs to standard services and characteristics (Battery Level is 0x2A19); these are shorthand for a 128-bit UUID built on the Bluetooth base UUID 0000xxxx-0000-1000-8000-00805F9B34FB. For your own services, generate random 128-bit UUIDs (for example with uuidgen). Never invent 16-bit ones.

In Figure 7.13, subscribe to the Telemetry characteristic's notifications, the way nRF Connect does when you tap its triple-arrow icon.
Subscribing is just an ATT Write Request of 01 00 to the characteristic's CCCD (UUID 0x2902). From then on the server pushes Handle Value Notifications without being asked. If notifications "don't work" in your own app, check first that it wrote the CCCD.

MTU and throughput

ATT packets are limited by the ATT MTU. The default is 23 bytes, of which 3 are the opcode and handle, leaving 20 bytes of value per notification or write. Both sides can negotiate a larger MTU (up to 517; 247 is a common choice because, with the Data Length Extension of Bluetooth 4.2, one 251-byte link-layer packet then carries a whole ATT packet). An RC command (throttle and steering as two 16-bit values) fits easily in 20 bytes, so MTU matters for telemetry and OTA, not for control. Real-world throughput depends on the connection interval, how many packets each side's stack allows per connection event, and the PHY: tens of kbit/s with defaults, up to about 1.3 Mbit/s with the 2M PHY and everything tuned.

After the client and server negotiate an ATT MTU of 247, what is the largest value a single notification can carry?
A notification spends 1 byte on the opcode and 2 on the handle.
\(247 - 3 = 244\) bytes. With the default MTU of 23 it's 20 bytes, the "20-byte BLE limit" you'll see in old forum posts.

An RC control service with NimBLE

On the ESP32 you have two BLE host stacks: Bluedroid (the default in older Arduino-ESP32 versions, large) and NimBLE (from Apache Mynewt; much smaller in flash and RAM). The NimBLE-Arduino library wraps NimBLE in a friendly C++ API. Here is the core of an RC car's GATT server: a write-without-response characteristic for drive commands, a notify characteristic for telemetry, and callbacks that stop the motors on disconnect. The code targets NimBLE-Arduino 2.x; version 1.x has slightly different callback signatures.

#include 

static const char* SVC_UUID   = "c0de0001-7a1e-4d1b-9b6b-5c0ffee00001";
static const char* DRIVE_UUID = "c0de0002-7a1e-4d1b-9b6b-5c0ffee00001";
static const char* TELEM_UUID = "c0de0003-7a1e-4d1b-9b6b-5c0ffee00001";

struct __attribute__((packed)) DriveCmd { int16_t throttle; int16_t steering; };  // -1000..1000

volatile uint32_t lastCmdMs = 0;
volatile DriveCmd cmd = {0, 0};
NimBLECharacteristic* telem;

class DriveCallbacks : public NimBLECharacteristicCallbacks {
    void onWrite(NimBLECharacteristic* c, NimBLEConnInfo& info) override {
        NimBLEAttValue v = c->getValue();
        if (v.size() != sizeof(DriveCmd)) return;          // validate everything from the air
        DriveCmd d; memcpy(&d, v.data(), sizeof d);
        cmd.throttle = constrain(d.throttle, -1000, 1000);
        cmd.steering = constrain(d.steering, -1000, 1000);
        lastCmdMs = millis();
    }
};

class ServerCallbacks : public NimBLEServerCallbacks {
    void onConnect(NimBLEServer* s, NimBLEConnInfo& info) override {
        // ask for 15 ms interval, no latency, 250 ms supervision timeout
        // (units: 1.25 ms, 1.25 ms, events, 10 ms)
        s->updateConnParams(info.getConnHandle(), 12, 12, 0, 25);
    }
    void onDisconnect(NimBLEServer* s, NimBLEConnInfo& info, int reason) override {
        cmd.throttle = 0; cmd.steering = 0;                 // failsafe on link loss
        NimBLEDevice::startAdvertising();                   // let the phone reconnect
    }
};

void setup() {
    NimBLEDevice::init("RC-Car");
    NimBLEServer* server = NimBLEDevice::createServer();
    server->setCallbacks(new ServerCallbacks());
    NimBLEService* svc = server->createService(SVC_UUID);
    svc->createCharacteristic(DRIVE_UUID, NIMBLE_PROPERTY::WRITE_NR)
       ->setCallbacks(new DriveCallbacks());
    telem = svc->createCharacteristic(TELEM_UUID, NIMBLE_PROPERTY::READ | NIMBLE_PROPERTY::NOTIFY);
    svc->start();
    NimBLEAdvertising* adv = NimBLEDevice::getAdvertising();
    adv->addServiceUUID(SVC_UUID);
    adv->setName("RC-Car");
    adv->start();
}

Write-without-response is the right property for control: a lost command is better replaced by the next one 20 ms later than retried, and unacknowledged writes can be sent several per connection event. Telemetry uses notify for the same reason.

Security, briefly

By default the service above is open: anyone in range with nRF Connect can drive your robot. BLE pairing creates encryption keys; bonding stores them so the devices reconnect securely later. The pairing method decides whether it resists eavesdroppers and man-in-the-middle attacks. "Just Works" pairing encrypts the link but authenticates nothing; LE Secure Connections with passkey entry or numeric comparison does both, but needs a display or keypad on at least one side. A robot without a screen can show a fixed passkey on a sticker (weak but better than nothing), or require a physical button press to accept new bonds. Then mark the drive characteristic as requiring an encrypted (or authenticated) link, so unpaired clients can't write to it.

Testing with nRF Connect

Nordic's free nRF Connect for Mobile app (Android and iOS) is the BLE equivalent of curl. It scans and shows advertising data and RSSI, connects, lists every service, characteristic and descriptor with their handles and properties, reads and writes raw values, and subscribes to notifications. Test your peripheral with it before writing any phone app: if nRF Connect can drive the car by writing E8 03 00 00 (throttle 1000, steering 0, little-endian) to the drive characteristic, the firmware is right and any remaining bugs are in the app. On a desktop, the nRF Connect apps or the Python bleak library do the same job.

Put the steps of a phone controlling the RC car over BLE in order.
  1. The car advertises on channels 37, 38 and 39
  2. The phone scans and receives an advertising packet
  3. The phone sends a connection request
  4. The phone discovers services and characteristics
  5. The phone writes 01 00 to the telemetry CCCD
  6. The phone writes drive commands; the car notifies telemetry
Advertise → scan → connect → discover → subscribe → exchange data. Service discovery results are often cached; subscriptions on a bonded device can persist too, which is a frequent source of "it works only the second time" bugs.

Antennas, keep-out zones and why your hand matters

The antenna on an ESP32 module is usually a PCB trace antenna: the meandering copper at the end of the module, outside the metal shield. It works by letting the high-frequency current in the trace radiate its fields into space (Chapter 1's fields, now at 2.4 GHz with a wavelength of 12.5 cm). Anything conductive nearby changes how it radiates: a ground plane under it, a battery, a motor, a metal chassis, your hand. Hence the module datasheets' keep-out zone: no copper on any layer under or around the antenna, and ideally the antenna sticking out past the edge of your PCB. Violate it and you can easily lose 10 dB, two-thirds of your range, without anything looking wrong.

Received signal strength falls quickly with distance. In free space the power spreads over a sphere, so it drops with the square of the distance; indoors, reflections and absorption make it fall faster. Engineers describe that in decibels (see Appendix A) with the log-distance model:

$$P_{rx} = P_{tx} + G_{tx} + G_{rx} - \underbrace{\left(PL_0 + 10\,n\log_{10}\frac{d}{d_0}\right)}_{\text{path loss}} - L_{\text{extra}}$$

Received power in dBm. \(PL_0 \approx 40\) dB at \(d_0 = 1\) m for 2.4 GHz; the exponent \(n\) is 2 in free space and roughly 2.5–4 indoors; \(L_{\text{extra}}\) collects bodies, walls and enclosures.

With \(n = 2\), doubling the distance costs \(20\log_{10} 2 = 6\) dB. So every 6 dB you lose to a bad enclosure halves your range in open air. A metal enclosure is a Faraday cage: it can cost 20–40 dB or more, turning a 50 m link into a 1 m one. A human body (mostly salt water, which absorbs 2.4 GHz strongly) between the antennas costs 10–20 dB, and a hand wrapped around a phone's antenna costs several more. Plastic enclosures are nearly transparent; carbon fibre is a conductor and behaves like metal.

In free space (path-loss exponent \(n = 2\)), by how many dB does the received signal drop when you double the distance?
\(10\,n\log_{10}(2)\) with \(n = 2\).
\(20 \log_{10} 2 = 6.02\) dB. Indoors, with \(n \approx 3\), it's about 9 dB per doubling, which is why indoor range is so much shorter than the datasheet's open-field figure.

Failsafe design: what happens when the link dies

Every wireless link fails eventually: the phone goes out of range, its screen locks and the app suspends, the battery sags and the radio browns out, a Wi-Fi router starts a big download on the same channel. The only question is what your robot does in the next half second. A car that keeps executing "full throttle" until it hits a wall is not a bug you want to discover in testing. The rule from hobby RC, enforced by every commercial receiver, is: on loss of signal, go to a safe state within a bounded time. For a car or a ground robot that's "motors stopped, steering centred"; for a plane it may be "throttle low, controls neutral" or a programmed return; for a multirotor it's a controlled descent or disarm.

A good failsafe has layers, each catching what the previous one misses:

  1. Command timeout (application layer). Timestamp every valid command. A periodic control task checks the age of the last one and, if it exceeds a timeout, stops the motors. This catches everything above the radio: a frozen phone app, a crashed BLE task, a full queue. The controller must send commands continuously (say every 20 ms), even when the sticks don't move, so silence always means trouble.
  2. Link-layer events. Handle onDisconnect by stopping the motors too. It reacts within the supervision timeout.
  3. Watchdog. If the firmware itself hangs, the watchdog resets the MCU, and…
  4. …hardware defaults. Pull-down resistors on motor-driver enable and PWM inputs make "MCU in reset or not yet booted" equal "motors off". Avoid strapping pins and pins that glitch at boot for these signals (see the ESP32 section).
  5. Validation. Reject malformed packets (wrong length, out-of-range values, bad checksum) instead of acting on them. Ramp-limit sudden changes so a single corrupted value can't slam the motors.

The timeout is a design trade-off you can compute. Too short, and ordinary packet loss trips it. Too long, and the robot travels too far blind. If commands arrive every \(T\) seconds and each is lost independently with probability \(p\), the timeout trips falsely when about \(m = \lfloor t_{out}/T \rfloor\) consecutive packets are lost, which starts with probability about \((1-p)\,p^m\) per packet. Meanwhile a vehicle at speed \(v\) covers \(v \cdot t_{out}\) after the link dies before it starts braking.

In Figure 7.15, with packet loss at 20%, choose a timeout that gives fewer than 0.1 false trips per hour while still stopping the car within 0.5 m of losing the link.
At 20% loss and 50 packets per second, you need about nine consecutive losses before a false trip is rare enough: \(180\,000 \times 0.8 \times 0.2^9 \approx 0.07\) per hour at 180 ms. The 0.5 m limit at 2 m/s caps the timeout at 250 ms. Anything from 180 to 250 ms works. If you can't find a window (say at 40% loss), the right fix is the link, not the timeout: send commands more often, move the antenna, or change radio.
// Control task: 100 Hz, independent of the radio
const uint32_t FAILSAFE_MS = 200;

void controlTask(void*) {
    TickType_t last = xTaskGetTickCount();
    for (;;) {
        uint32_t age = millis() - lastCmdMs;         // lastCmdMs written by the BLE callback
        int16_t thr = cmd.throttle, steer = cmd.steering;
        if (age > FAILSAFE_MS) { thr = 0; steer = 0; }   // safe state
        setMotor(rampLimit(thr));                     // limit acceleration even when healthy
        setServo(1500 + steer / 2);                   // µs: 1000..2000
        esp_task_wdt_reset();                         // only reached if this loop is alive
        vTaskDelayUntil(&last, pdMS_TO_TICKS(10));
    }
}
Which of these belong in a robust RC failsafe? (Select all that apply.)
  1. The controller sends commands periodically even when the sticks don't move
  2. The robot stops the motors if no valid command has arrived for a set time
  3. The robot keeps the last command until the user reconnects, to avoid jerky motion
  4. Pull-down resistors keep the motor driver disabled while the MCU is in reset
  5. Malformed or out-of-range packets are discarded
  6. The failsafe relies only on the BLE disconnect callback
Holding the last command is exactly the runaway you're trying to prevent. The disconnect callback alone fires only after the supervision timeout, and never if the phone stays connected while its app has frozen. Layers: periodic commands, a timeout, link events, a watchdog and hardware defaults.

  5. Add telemetry: notify the battery voltage (from the ADC1 pin, calibrated) and the RSSI once a second.
  6. Range test: note the RSSI at 1, 2, 5, 10 and 20 m in line of sight, then with your body between phone and car, then with the ESP32 inside a metal tin. Plot RSSI against log distance and estimate the path-loss exponent.
  7. Robustness: unplug the battery mid-drive, pull the reset pin, and let the watchdog fire (add a deliberate infinite loop on a hidden command). Every case must end with the motors stopped.
